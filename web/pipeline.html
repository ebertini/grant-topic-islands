Stage 0 — Ingest

0ingest.py data/raw/<DATASET>.csv → grants.normalized.jsonl code
reads raw CSV  →  writes {id, title, abstract, funder, funder_code, year} per line
  • decision: column-header sniffing picks one of two adapters — legacy (grant_id/agencyname/abstract) or nsf_award_export (awd_id/corpus/div_abbr, whose true abstract is recovered by stripping the title prefix off a title+abstract-concatenated corpus field). Unknown headers → hard error, nothing written.
  • filter: drop duplicate titles (same title seen before, case-insensitive) — NSF "Collaborative Research" awards are split one row per institution but share a title/abstract; left in, they'd inflate downstream document-frequency counts.
  • filter: drop rows with empty abstract, or abstract < MIN_ABSTRACT_CHARS = 100 chars (too little topical signal).
  • funder name normalized (e.g. strips "‑ SubAward" suffix); year parsed and range-checked to 1950–2100 or left null.

Stage 1 — Clean

1clean.py grants.normalized.jsonl → grants.clean.jsonl + stopwords.txt code
reads normalized docs  →  writes cleaned abstract text + a corpus-specific stopword list consumed by stage 2
  • HTML/entity sanitation: literal tags and upstream "and‑mangled" entities (andlt for &lt;) removed as one unit so a real "Br" (bromine) isn't eaten.
  • strips the leading <award_id> <PI name(s)> header NSF abstracts carry, and boilerplate review-criteria sentences ("intellectual merit and broader impacts...").
  • decision (data-driven): any term appearing in ≥ HIGH_DF = 30% of abstracts is grant-generic filler → added to the domain stoplist for stage 2's KeyBERT vectorizer (not used by the current LLM-based stage 2, see below).
  • manual list: a curated SEED_STOPWORDS set (research, project, study, pi, nsf, university, intellectual, merit, ...) is unioned in regardless of frequency.
  • manual override: a PROTECT set (data, systems, gene, protein, model, ...) is exempted even if high-DF — generic alone, but the backbone of real keyphrases like "data science".
Note: stage 1's stopword list only feeds the vanilla KeyBERT extractor (keywords.py). The pipeline currently in the README uses the LLM extractor (keywords_llm.py), which filters generic language via prompt instructions instead — see Stage 2.
↓

Stage 1.5 — Filter to research grants (LLM decision)

1.5filter_research.py grants.clean.jsonl → grants.research.jsonl (kept) / grants.excluded.jsonl (dropped) LLM
model claude-haiku-4-5, one classification call per grant (Message Batches API)  ·  reads title + first 1,500 chars of abstract
  • LLM call: classifies each grant's PRIMARY purpose into one of 9 categories: research, tool_or_infrastructure, evaluation_research, training, conference_or_travel, education_or_curriculum, outreach_or_broadening_participation, economic_development, other.
  • policy in code, not the model: KEEP_TYPES = {research, tool_or_infrastructure, evaluation_research} — the model only returns a category, this constant decides what survives. Changing the policy (stricter, or "flag for review") needs no re-classification.
  • filter: everything else is moved to grants.excluded.jsonl with the model's category + a ≤12‑word rationale — the record is never destroyed, just set aside.
  • a grant the model fails to classify (bad JSON, API error) is kept as a fallback rather than silently dropped.
This is the largest content-based filter in the pipeline: 841 of 4,692 grants (18%) dropped here in the active dataset — mostly conference/travel and training awards.
↓

Stage 2 — Keyphrase extraction (LLM decision, active path)

2keywords_llm.py grants.research.jsonl → grants.keywords.jsonl LLM
model claude-haiku-4-5, one call per grant  ·  reads title + first 2,500 chars of abstract
  • LLM call: returns 3–12 keyphrases (fewer if the abstract has little specific content — the model is told never to invent filler), each with a 1–5 salience rating.
  • prompt rule: exclude generic grant/admin language (research, objectives, broader impacts, workforce, outreach…), institution names, people, places, and program names (CAREER, REU, GRFP…).
  • prompt rule — canonicalization: lowercase, singular, standardized acronyms (expand "ML" → "machine learning"; keep universal ones like "dna", "mri"), variants merged to one form — this is what keeps stage 3's vocabulary from fragmenting.
  • score stored = salience / 5 (so 0.2–1.0), same schema as the alternate KeyBERT path so downstream stages don't care which extractor ran.

Stage 2 (alternate, not in the active pipeline)

2′keywords.py grants.clean.jsonl + stopwords.txt → grants.keywords.jsonl code
deterministic KeyBERT extraction — kept for comparison, not run by the README's current pipeline order
  • embedder intfloat/e5-large-v2; candidates restricted to grammatical noun phrases via spaCy POS pattern <J.*>*<N.*>+ (KeyphraseVectorizers), avoiding "word salad".
  • stopwords = sklearn English list ∪ stage 1's domain stoplist. TOP_N = 15 keyphrases/doc, MMR DIVERSITY = 0.5 to reduce near-duplicates.
↓

Stage 3 — Hierarchical clustering

3cluster.py grants.keywords.jsonl → topics.json + topic_centroids.npy code
embedder all-MiniLM-L6-v2  ·  one Ward-linkage dendrogram, cut twice for strict nesting
  • filter: vocabulary = keyphrases with document frequency ≥ MIN_DF = 3 — a phrase only one or two grants use is dropped from clustering (it still exists on its source grants, just isn't a cluster-forming term). 2,158 of the full keyphrase set qualify in the active dataset.
  • parameter: the same dendrogram is cut at N_TOP = 18 (level‑1 topics) and N_SUB = 90 (level‑2 subtopics) via fcluster(..., criterion="maxclust") — one tree, two cut heights, so every subtopic nests inside exactly one topic by construction.
  • each cluster's label comes from class-based TF‑IDF over its member keyphrases' tokens (BERTopic-style: frequent-in-cluster, rare-in-siblings) — LABEL_TERMS = 6 terms kept, top 3 form the c‑TF‑IDF label (superseded for display by stage 3b's LLM label).
  • topics ordered by aggregate keyword score (biggest first); each node also carries a funder mix (share of docs by funder code).
↓

Stage 3b — Topic labels (LLM decision, cosmetic only)

3blabel_llm.py topics.json → topics.json (adds llm_label) LLM
model claude-opus-4-8, a single structured-output call for all clusters at once (18 + 90 = 108 nodes)
  • LLM call: given each cluster's c-TF-IDF terms + top 10 member keywords, returns a 2–5 word Title Case label naming the actual research area — or plainly flags administrative/non-research clusters ("Program Administration", "Place Names") rather than forcing a research-sounding name onto noise.
  • doesn't change which documents belong where — label (c‑TF‑IDF) is kept alongside llm_label; only display labelling is affected.
↓

Stage 4a — Seed layout & doc index

4aseed_layout.py topics.json + topic_centroids.npy + grants.keywords.jsonl → topics.json code
  • method choice: 2D layout via MDS on cosine distance between the 18 topic centroids — not UMAP, because UMAP is unstable with that few points, while MDS on a precomputed distance matrix is deterministic (fixed random_state=42) and appropriate at this scale.
  • coordinates scaled to [0,1] — this is the semantic "seed" position islands start from in the frontend layout.
  • builds the docs metadata index (title/funder/year/abstract) for every grant referenced by any surviving keyword, and tags each keyword leaf with its dominant funder (majority vote over its source docs) for the frontend's funder colouring.
↓

Stage 4b — Document coverage

4bcoverage.py topics.json + grants.keywords.jsonl → topics.json code
  • decision rule: a grant is "covered by" a subtopic if it contains ≥ 1 of that subtopic's keyphrases (union / "at least one" rule, not majority or exclusive assignment) — so a grant can, and often does, count toward several subtopics and topics.
  • consequence: topic doc_count values sum to more than the total document count (overlap by design); a topic's own count is exactly the union of its subtopics' doc sets (nesting still holds even though sibling topics overlap).
  • computed from the full (uncapped) keyword→document links, because each keyword's stored docs list is capped at 50 in the JSON the browser loads — this recomputation is why the stage exists as a separate offline step.
↓

Stage 5 — Activate

5activate.py data/processed/<DATASET>/topics.json → data/processed/topics.json code
  • decision: the frontend always fetches the one fixed path data/processed/topics.json; every other stage is scoped per‑DATASET, so several datasets' full artifact chains can sit on disk simultaneously. This script is the single seam that decides which one is "live" — it's a plain file copy, no recomputation.
  • switching datasets (e.g. back to the original grants corpus) is just re-running this one script with a different DATASET — nothing upstream needs to re-run.
